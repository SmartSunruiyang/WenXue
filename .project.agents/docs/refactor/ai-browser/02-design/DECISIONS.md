## ADR-001：基于 Chromium //chrome 构建问学浏览器

- 状态：Accepted
- 日期：2026-07-14
- 决策域：浏览器内核与产品形态

### 决策

以 Chromium 的 //chrome 产品层为基础构建问学浏览器，在浏览器源码内实现品牌化 UI、任务工作台、任务隔离和内置问学 MV3 扩展。首版保留标准浏览器语义，不从零实现浏览器内核，也不采用仅嵌入网页视图的壳层作为目标架构。

### 原因

- 需要完整地址栏、导航、多标签页、权限、下载、站点隔离和开发者工具等浏览器基础能力；
- 需要对浏览器 UI、任务模型和扩展生命周期进行产品级控制；
- 最大化复用 Chromium 已验证的安全、兼容性和性能机制；
- 为现有 Chrome 扩展能力迁移提供最接近的运行环境。

### 后果

- 必须承担 Chromium 分支维护、构建、签名、更新和安全响应成本；
- 私有补丁要尽量收敛在明确的问学模块与薄集成点，减少上游合并冲突；
- 浏览器级性能目标应通过对称基线验证，不能仅凭“使用 Chromium”宣称与 Chrome for Testing 等价。

### 验证

G1 产出 macOS arm64 和 Windows x64 可重复构建；G3 完成扩展能力等价；G4 完成性能与稳定性基线。

## ADR-002：任务是持久化、隔离且可并行的浏览器环境

- 状态：Accepted
- 日期：2026-07-14
- 决策域：任务与数据隔离

### 决策

每个任务对应一个持久化任务浏览器环境，至少拥有独立的 Profile/user-data-dir、Browser/TabStrip、站点数据、权限、历史、密码与扩展存储。任务可以同时存在、同时加载页面并同时运行 Agent；任务切换只改变前台展示，不暂停其他任务。

“任务”是通用容器，不按 Research、答题等业务类型拆分。

### 原因

- 用户明确要求不同任务登录态不共享；
- 多标签页 Agent 必须在明确的任务边界内工作；
- 并行任务需要能够独立停止、失败、等待和恢复，避免共享可变状态导致串扰。

### 后果

- 登录态、Cookie、Cache、Storage、Service Worker、权限、历史和问学扩展状态均按任务隔离；
- 所有 Agent 指令、标签页句柄、事件与结果必须带 taskId，并在执行前复核归属；
- 一个任务关闭、崩溃或等待用户操作，不得影响其他任务；
- 内存占用会随活跃任务增加，需要后台冻结、回收和恢复策略，但不得破坏隔离语义。

### 验证

G2 至少用两个并行任务验证独立登录、持久化恢复、标签页归属和故障隔离；G4 进行多任务长稳与资源测试。

## ADR-003：账号控制面与任务浏览凭证分离

- 状态：Accepted
- 日期：2026-07-14
- 决策域：认证与安全

### 决策

问学账号登录属于应用控制面，不直接复制到任务 Profile。任务获得短时、最小权限的网关凭证。用户主动委托的站点凭证只允许在指定任务和指定 Agent run 范围内使用；任务间不共享 Cookie 或站点登录态。

### 原因

- 避免把问学账号会话或敏感令牌暴露给任意网页与扩展上下文；
- 保持任务隔离，限制凭证泄漏后的影响面；
- 支持审计、吊销和最小权限授权。

### 后果

- 需要明确凭证签发、刷新、吊销和过期行为；
- Agent 侧不得持久化明文主令牌；
- BYO 凭证传递需要专门的用户确认、作用域和审计记录。

### 验证

G2 完成威胁建模及跨任务泄漏测试；G3 验证扩展、页面与原生层之间的凭证边界。

## ADR-004：应用仓库与 Chromium 分支仓库分离

- 状态：Accepted
- 日期：2026-07-14
- 决策域：源码与交付

### 决策

保留 WenXue 仓库承载产品服务、共享协议、迁移工具和现有运行时；新建 wenxue-chromium 仓库承载 Chromium 分支、问学浏览器模块和构建配置。发布清单必须把两个仓库 commit、Chromium revision、扩展版本与协议版本绑定为一个可追溯版本。

### 原因

- Chromium 仓库体量、工具链、提交历史和发布节奏与应用仓库显著不同；
- 分离可降低现有产品仓库的克隆和 CI 成本；
- 发布清单仍能保证跨仓库版本一致性。

### 后果

- G1 前必须明确新仓库的远端、权限、责任人和分支策略；
- 协议变更需使用兼容窗口或原子升级规则；
- CI/CD 必须验证跨仓库版本组合，不能依赖开发者本地约定。

### 验证

G1 生成带完整源码坐标和哈希的构建产物与 SBOM。

## ADR-005：新旧运行时在迁移期并存

- 状态：Accepted
- 日期：2026-07-14
- 决策域：迁移与回滚

### 决策

Electron + Chrome for Testing 现有运行时在目标浏览器达到发布门禁并经过稳定窗口前继续保留。新运行时采用受控灰度；用户数据迁移是可重试、可验证和可回滚的，旧数据在确认前不被破坏性修改。

### 原因

- 浏览器内核迁移涉及用户数据、扩展行为、系统集成和发布链路，单次切换风险过高；
- 旧运行时是验证行为等价和性能对称比较的基线；
- 灰度和回滚能限制不可预见的站点兼容与数据问题。

### 后果

- 迁移期需要维护明确的兼容边界，避免无限期双写；
- G5 后仍需保留约定的回滚窗口；
- G6 必须有明确退场标准，不以“基本可用”代替完成。

### 验证

G4 完成迁移/回滚演练；G5 完成灰度发布；G6 在稳定窗口结束后评审旧运行时退场。

## ADR-006：TaskBrowserHost 的窗口承载机制

- 状态：Pending G2 Spike
- 日期：2026-07-14
- 决策域：浏览器窗口与工作台承载

### 待决问题

目标产品必须表现为一个问学工作台：左侧任务列表、当前任务标签页与右侧 AI 侧边栏。底层可选择：

1. 在单一主窗口内直接承载多个任务的 Browser/TabStrip；
2. 使用不对用户暴露的 backing windows，并将当前任务安全附着到主工作台；
3. 采用经 Spike 证明等价的其他 Chromium 原生承载方式。

### 选择标准

- 不破坏 Chromium 的导航、权限、弹窗、下载、无障碍和输入事件语义；
- 后台任务可继续运行，但不得抢占焦点、弹出非授权窗口或串用当前任务 UI；
- 任务切换稳定，无标签页归属错乱；
- 上游合并成本与私有补丁面可控；
- macOS 与 Windows 行为一致。

### 当前约束

无论内部机制为何，产品默认不向用户展示“每个任务一个独立窗口”。实现不得把内部 backing window 当成产品信息架构。

### 验证与决策时点

G2 前完成最小 Spike，对焦点、弹窗、权限、下载、崩溃恢复和资源占用进行对比。结论写入新的 Accepted ADR，并同步 ARCHITECTURE、PLAN、TESTING 和 UIUX。
